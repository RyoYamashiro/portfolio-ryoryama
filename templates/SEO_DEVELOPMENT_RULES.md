2026-10-29にユーザー提供資料を取り込み、既存方針と統合した。
このファイルは設計・実装時の判断基準、[SEO共通チェックリスト](SEO_COMMON_CHECKLIST.md) は公開・運用時の確認項目として使う。共通項目を変更する場合は両者の整合も確認する。

- 重要本文の初期HTML出力は本プロジェクトの実装原則とする。特定の描画方式自体をGoogleの必須要件とは説明しない。
- サイトマップは既存チェックリストに合わせ、本プロジェクトでは公開時の標準要件とする。下記のP1分類を理由に省略しない。
- CMS・ブログはSEOだけを理由に追加しない。ただし今回のジム商品では既存の開発目標であり、この資料の一般論だけで削除しない。範囲は [ジム特化の計画](docs/gym-business-plan.md) に従う。
- Next.jsのファイル拡張子は現行のJavaScript構成に合わせてよい。`.ts` の例だけを理由にTypeScript移行を必須化しない。
- 各変更で関連項目を確認し、公開前に全体を点検する。文書のみの変更にはページ実装の検証レポートを要求しない。
- 外部サービスの設定・実測データ不足は、実装済みと区別して担当・残作業を記録する。権限のない設定を完了扱いにしない。

以下は提供資料の基準。仕様が変わり得る項目は、実装時に公式資料で確認する。今回の取り込み自体は最新仕様の検証やSEO実装の完了を意味しない。

> Webサイト開発用・SEO品質基準 / 2026-10
>
> **このファイルは開発AIに常時適用する指示書です。** 新規開発・既存サイト改修・リファクタリング・公開作業の際に、以下の要件を確認してください。
> 対象：Next.js / React / WordPress / 静的サイト / CMS連携など。特に店舗サイト・サービスサイト・ブログを想定します。

## 0. 最上位の原則

1. **SEOを後付けにしない。** URL設計、ページ構造、メタ情報、クロール／インデックス、表示速度、内部リンクを設計時点から考慮する。
2. **検索エンジンよりユーザーを優先する。** 検索意図に合った正確で独自性のある情報を、読みやすく提供する。キーワードの不自然な詰め込みや薄い量産ページを作らない。
3. **技術的SEOは自動化する。** 共通要件はコードやテンプレートで標準実装し、運営者に不要な設定作業を強いない。
4. **Googleの公式ドキュメントと実際の仕様に従う。** フレームワークの最新APIやGoogleの仕様が変わっている可能性があれば公式資料を確認する。憶測を順位要因として断定しない。
5. **施策の効果を誇張しない。** 構造化データ、Core Web Vitals、サイトマップ等の整備だけで検索順位・インデックス・リッチリザルト表示は保証されない。
6. **規模に応じて実装する。** 1ページの店舗サイトにブログ・CMS・多言語化等を無理に追加しない。必要な機能だけを、将来拡張可能な形で実装する。

## 1. 必須の技術的SEO（全サイト）

### 1-1. クロール・レンダリング・インデックス

- 公開対象の重要コンテンツ（店舗名、サービス、料金、所在地、本文など）は**初期HTMLで取得できる**構成を原則とする。Next.jsなら静的生成（SSG/ISR）またはサーバーレンダリング（SSR）を適切に選択する。
- SPAのクライアント描画だけに重要コンテンツを依存させない。重要リンクはクロール可能な`<a href="...">`で提供する。
- 公開ページが正常に`200`を返し、削除ページは適切に`404`/`410`、恒久移転は`301`/`308`を返すこと。
- `robots.txt`を用意し、クロールを妨げるルールを誤って設定しない。**robots.txtのDisallowはインデックス削除手段ではない。** インデックス除外には適切な`noindex`等を用いる。
- 本番の重要ページに誤った`noindex`、認証制限、canonical、JavaScript依存、リダイレクトループがないか確認する。
- ステージング／プレビューは検索対象にしないよう制御し、本番公開時には意図しない制御が残っていないことを確認する。

### 1-2. メタデータ・URL

- 各検索対象ページに、**固有で内容に即した`<title>`**を設定する。
- 各ページに、内容を正確に要約した`meta description`を設定する。これは主に検索結果での説明文候補であり、直接的な順位向上を保証するものではない。
- ページの主題を明確にする`h1`を適切に配置し、`h2`以降で論理的な見出し階層を作る。
- 意味のある短いURLを使い、不要なパラメータや重複URLを増やさない。
- 各インデックス対象ページに、基本的に適切な自己参照`canonical`を設定し、正規URLを統一する。**canonicalはヒントであり、絶対命令ではない。**
- HTTPSを利用し、wwwの有無・末尾スラッシュ等のURLの揺れを整理する。
- URL変更時は旧URLから対応する新URLへ恒久リダイレクトを実装する。無関係なページへ一括転送しない。

### 1-3. サイトマップ・内部リンク

- `sitemap.xml`を自動生成する。原則として**正規・公開・インデックス対象のURLのみ**掲載する。更新日時は実際の更新に合わせる。
- `robots.txt`にサイトマップの場所を記述する。
- 重要なページがトップ・ナビゲーション・関連ページ・フッター等から自然にたどれるようにする。
- 適切な場合はパンくずナビゲーションを設ける。
- 孤立ページ、リンク切れ、不要なリダイレクト連鎖を作らない。

### 1-4. モバイル対応・使いやすさ

- モバイルファーストで設計する。スマホでも主要コンテンツ・リンク・構造化データが欠落しないようにする。
- セマンティックHTMLを優先する（`header`、`nav`、`main`、`section`、`article`、`footer`など）。
- 文字が読め、ボタンが押せ、レイアウトが崩れないこと。アクセシビリティも品質要件として扱う。

## 2. パフォーマンス（Core Web Vitals）

**実ユーザーデータの75パーセンタイルでの「良好」基準：**

| 指標 | 目標 |
| --- | --- |
| LCP（最大コンテンツの表示） | 2.5秒以下 |
| INP（操作への応答） | 200ms以下 |
| CLS（レイアウトのずれ） | 0.1以下 |

- 画像を適切に圧縮・リサイズし、必要に応じてWebP/AVIF、レスポンシブ画像を利用する。
- 画像に`width`/`height`またはアスペクト比を指定し、レイアウトシフトを防ぐ。
- ファーストビューの主要画像（LCP候補）を無条件に遅延読込しない。画面外画像は適宜遅延読込する。
- 不要なJavaScript、重いライブラリ、外部タグ、フォントの読み込みを抑える。
- キャッシュ、静的生成、CDN等をプロジェクトに応じて利用する。
- Lighthouseだけでなく、PageSpeed Insights / Search Consoleの実測データで評価する。初期段階で実測データが少ない場合はラボデータも参考にする。
- **Lighthouse 100点は必須条件でも順位保証でもない。** 数値のためにコンテンツ品質や機能を犠牲にしない。

## 3. 構造化データ（JSON-LD）

- ページの実態と一致する構造化データのみ実装する。Googleがサポートするタイプ／必須・推奨プロパティを公式仕様で確認する。
- 必要に応じて以下を選択する。**全タイプを機械的に載せない。**
  - 店舗：`LocalBusiness`、業種に合うサブタイプ（例：ジムなら`HealthClub`）
  - 運営組織：`Organization`
  - サイト：`WebSite`
  - パンくず：`BreadcrumbList`
  - ブログ記事：`BlogPosting` / `Article`
  - 人物の紹介：`Person`（必要な場合）
- 実在しないレビュー、評価、資格、価格、営業情報、住所を生成しない。
- `FAQPage`を追加しても、一般的な店舗サイトでFAQリッチリザルトの表示は基本的に期待しない。
- GoogleのRich Results TestおよびSchema Markup Validator等で構文・対象性・ページ内容との整合を確認する。
- **構造化データの存在だけで検索順位やリッチリザルトの表示は保証されない。**

## 4. コンテンツSEO・信頼性

- ページごとに「誰が、どんな検索意図で、何を解決したくて訪れるか」を定義する。
- サービス名、料金、特徴、対象者、利用の流れ、よくある疑問、所在地、問い合わせ導線を必要に応じて明確化する。
- 実際の写真、実績、運営者情報、専門資格、更新情報、出典など、**事実に基づく独自の根拠**を優先する。
- AIで大量生成しただけの似たページ、地域名を差し替えただけのページ、根拠のない比較・体験談は作らない。
- 必要なキーワードは自然な日本語の中で適切に使用する。キーワード密度を目標値として設定しない。
- E-E-A-T（経験・専門性・権威性・信頼性）はコンテンツの評価観点であり、**単一の数値スコアや独立した直接的ランキング要因として扱わない**。
- SEOのために文章量を無意味に増やさない。ユーザーに必要な情報が満たされていることを重視する。

## 5. 店舗サイトのローカルSEO（該当する場合は必須）

- Googleビジネスプロフィール（GBP）と公式サイトの情報を整合させる。
- 店舗名・住所・電話番号（NAP）、営業時間、サービス内容、公式サイトURLを正確に掲載する。
- 店舗ページには実際のアクセス方法、地域情報、設備、料金、予約／問い合わせ導線を含める。
- 必要に応じて地図・アクセスリンクを配置する。
- 口コミの偽装、レビュー購入、評価の恣意的な構造化データ化はしない。
- ローカル検索はGoogleが説明する**関連性・距離・知名度**等に左右される。サイト制作だけでマップ順位が上昇するとは約束しない。
- GBPの設定や運用はサイト内の実装とは別作業。権限がない場合は、設定が必要な項目を引き渡し事項として明記する。

## 6. AI検索（AI Overviews / AI Modeなど）

- Google公式のSEO基本原則に従い、独自性・信頼性・情報の明確さを高める。
- AI専用の特殊なタグや`llms.txt`を**Google検索での上位表示の必須条件として扱わない**。
- 通常検索から見られないページ、誇張したFAQ、検索エンジン向けだけの不自然な文章を増やさない。
- AIによる引用・表示はコントロールや保証ができないことを前提にする。

## 7. Next.jsプロジェクトでの実装方針

Next.js App Routerを採用する場合（使用バージョンに応じて公式APIを確認）：

- `generateMetadata` / `metadata`でページ固有のタイトル、説明、canonical、OGP等を管理する。
- `app/sitemap.ts`、`app/robots.ts`でサイトマップとrobots設定を管理する。
- JavaScript構成では対応する `.js` を使用できる。利用できるAPIはインストール済みのNext.jsの資料で確認する。
- 動的ページはSSG/ISR/SSRを適切に使い分け、インデックス対象の本文をサーバー側で出力する。
- `next/image`等を適切に使い、画像サイズ・優先読込・遅延読込を制御する。
- JSON-LDはページデータから安全に生成し、実際の表示内容との不一致を防ぐ。
- CMSを使用する場合は、タイトル、説明、スラッグ、画像、公開状態、更新日時等の入力・検証を設計する。
- サイトの正式URL（例：`SITE_URL`環境変数）を一元管理し、開発・プレビュー・本番でcanonicalやsitemapが混在しないようにする。
- **CMSはSEOの必要条件ではない。** ブログ更新が不要な1ページサイトなら静的コンテンツで十分。

## 8. 分析・計測（公開時の引き渡し要件）

- Google Search Console（GSC）で、サイト所有権確認、インデックス状態、検索クエリ、エラーなどを確認できるようにする。
- 要件に応じてGA4を導入し、問い合わせ、予約クリック、電話クリック等の重要なコンバージョンを計測する。
- タグ導入にあたり、適用されるプライバシー・同意要件を確認する。
- GSC・GA4の管理権限がない場合は、実装できる範囲と運営者側で必要な設定を分離する。
- OGPはSNS共有品質として実装するが、直接的なGoogle順位向上施策として説明しない。

## 9. 優先度とスコープ判断

| 優先度 | 内容 | 方針 |
| --- | --- | --- |
| P0：必須 | 検索可能なHTML、正しいHTTPステータス、robots/noindex確認、モバイル、基本メタ情報、正規URL、内部リンク、実在する店舗情報 | 公開前に必ず対応 |
| P1：強く推奨 | sitemap、必要なJSON-LD、画像最適化、Core Web Vitals、パンくず（複数階層なら）、GSC、GBP連携支援 | 該当する範囲で標準実装 |
| P2：必要時のみ | CMS、ブログ、多言語hreflang、追加Schema、詳細な分析タグ、複雑なコンテンツ施策 | 実際の要件と予算がある場合に導入 |

**1ページ・低価格テンプレートの原則：** P0を妥協せず、該当するP1を軽量に実装する。更新頻度の低いサイトにCMSや複雑な運用フローを無理に組み込まない。

## 10. 開発AIへの作業命令

**新規ページを作成・変更するときは、必ず次を実行すること。**

1. 変更対象ページの検索意図、公開対象・非公開対象、URL構造を確認する。
2. 本文が検索エンジンから取得できるか、メタ情報・canonical・内部リンク・構造化データが適切かを確認する。
3. モバイル表示、画像、CLSを含む速度要因、リンク切れ、ステータスコードを確認する。
4. 既存ページのURLやSEOメタ情報を変更する場合は影響を確認し、必要なリダイレクトを実装する。
5. 計測やGBPの外部アカウントが必要な作業は、実装と人間側の設定作業を明確に分ける。
6. 不確かなSEO施策を必須要件として追加せず、根拠と必要性を示す。
7. 作業終了時に以下のフォーマットで報告する。**未検証の項目を「確認済み」と書かないこと。**

```text
【SEO実装・検証レポート】
- 対象ページ／変更箇所：
- 実装したSEO対策：
- 検証した項目と結果：
- 未検証事項とその理由：
- 外部サービス側で必要な設定（GSC/GBP/GA4等）：
- 残課題と優先度（P0/P1/P2）：
```

## 11. 公開前の最終チェック

- [ ] 本番ページに意図しない`noindex`・robotsブロックがない
- [ ] `title`・`meta description`・`h1`が適切で、重複や空欄がない
- [ ] 本文と重要リンクがHTMLから取得できる
- [ ] canonical、https、URL統一、ステータスコードが適切
- [ ] `sitemap.xml`にインデックス対象の正規URLが載っている
- [ ] 内部リンク切れ・不要なリダイレクトがない
- [ ] スマホ表示・操作・主要コンテンツに問題がない
- [ ] 画像の代替テキスト・サイズ・読み込み方法が適切
- [ ] JSON-LDが実ページの事実と一致し、該当する場合に検証済み
- [ ] 店舗名・住所・電話番号・営業時間・料金が正確（店舗サイトの場合）
- [ ] Core Web Vitalsを計測、または未計測理由を明記
- [ ] GSC / GA4 / GBPの設定状況と担当範囲を明記
- [ ] 実測できないSEO効果や順位上昇を保証する表現がない
