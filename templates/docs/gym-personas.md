# ジム商品の顧客ペルソナ

対象顧客の定義は [共通の事業方針](business-policy.md) を参照する。以下は開発の焦点を絞るための架空の人物で、実在顧客や調査結果ではない。年齢・性別から能力や好みを決めつけず、実際の営業・操作確認で検証する。
ここで扱うのはサイトを購入・更新する経営者。ジムに通う来店客のペルソナとは区別する。

## 1. 佐藤 悠太・32歳：独立したばかりの一人ジム経営者

**状況の仮説：** 指導と営業を一人で担当。Instagramで実績や日常を発信しているが、公式サイトはない。Googleマップから料金や体験案内へつなげたい。

- 望み：小さくても「ちゃんとしたジム」に見えるサイトを持ち、問い合わせのたびに同じ説明をする手間を減らしたい。
- 不安：安い制作には追加費用がありそう。何を準備すればよいか分からず、設定を調べ続ける時間もない。
- 操作の前提：スマートフォンのSNS操作には慣れているが、ドメイン・サーバー・CMSは詳しくない。
- 購入の判断：完成形と総費用が分かるか。自分が提供する情報と、制作側が対応する作業が明確か。
- 言いそうなこと：「営業中に何度も連絡を返すのは大変。必要なものをまとめて教えてほしい」

**開発への反映：** 素材提出リスト、初期値のある最小限の設定、明確な料金表・アクセス・体験予約導線を優先する。
**確認する操作：** 必要な素材をそろえ、体験予約先を設定し、公開後のサイトをスマホで確認できるか。

## 2. 高橋 美咲・37歳：店舗の雰囲気を大切にするオーナートレーナー

**状況の仮説：** 一店舗を運営し、紹介とInstagramが主な接点。既存の簡易ページはあるが、現在のサービス内容や店の雰囲気が十分に伝わっていない。

- 望み：初心者が安心して来られる雰囲気と、自分の指導へのこだわりを伝えたい。写真や体験料金を自分で更新したい。
- 不安：いかにも量産されたデザインになること。変更するとレイアウトを壊してしまうこと。
- 操作の前提：写真選びや投稿はできるが、コードや複雑な管理画面には触れたくない。
- 購入の判断：実際の写真を入れたときに店らしく見えるか。どこまで自分で変更できるか。
- 言いそうなこと：「おしゃれにはしたい。でも、初めての人が入りづらい雰囲気にはしたくない」

**開発への反映：** 写真・紹介文・料金の安全な差し替え、読みやすいデザイン、プレビュー、更新項目の分かりやすい名称を優先する。
**確認する操作：** 紹介文と写真を変え、見た目を確認して公開できるか。編集場所に迷うなら簡単モードの検証材料にする。

## 3. 中村 健一・42歳：更新の外注負担を減らしたいジム経営者

**状況の仮説：** 一店舗を複数トレーナーで運営。既存サイトはあるが、料金やスタッフの変更を外注しており、情報が古くなりやすい。

- 望み：必要な更新を短時間で済ませ、サイト管理に追われず店舗運営へ集中したい。
- 不安：契約後に維持費や作業が増えること。更新の失敗や、乗り換えで既存URL・問い合わせ導線が失われること。
- 操作の前提：業務用の予約サービスなどは使える。新しいツールを覚える負担は抑えたい。
- 購入の判断：運用費とサポート範囲が明確か。既存サイトから移せる範囲を説明してもらえるか。
- 言いそうなこと：「毎日触るわけじゃないから、久しぶりでも迷わず更新できるようにしたい」

**開発への反映：** 料金・トレーナーの更新、保存・公開状態の明示、短い操作手順を優先する。移行はURLや契約条件を確認して別途範囲を決め、標準価格に無条件で含めない。
**確認する操作：** 料金とトレーナー情報を更新し、公開結果を確認できるか。操作が止まる箇所と必要な支援を記録する。

## 3人を軸にした優先順位

主軸は佐藤さんの「初めて公式サイトを持つ負担を減らす」。高橋さんでデザインと更新の分かりやすさ、中村さんで継続運用の負担を確認する。これは初期の作業上の優先案であり、実顧客の反応で見直す。

| 優先するもの | 3人に共通する価値 |
| --- | --- |
| デモ・料金・提供範囲の明示 | 購入前に完成形と負担を判断できる |
| 店舗・サービス・料金・トレーナー・予約導線 | 来店客に必要な情報をまとめて伝えられる |
| 少ない入力項目と分かりやすい保存・公開 | 更新に迷いにくく、誤操作を減らせる |
| スマホでの読みやすさと操作確認 | 日常の端末で閲覧・更新できるか確かめられる |
| 導入チェックリストと短いマニュアル | 初回と久しぶりの操作の負担を減らせる |

個別の要望を全部積み上げず、共通する困りごとから着手する。簡単モードは通常モードの操作確認後に検討し、複数店舗管理・独自予約・全面カスタマイズは現時点の必須範囲にしない。
お知らせ・ブログなど既存の計画は維持しつつ、利用頻度と更新負担を検証する。架空の人物設定だけを根拠に必須機能を増減しない。

## 使い方と検証

要件・デザイン・実装・マーケティング・営業の判断時に「誰の、どの困りごとに効くか」を確認する。
購入者の年齢を来店客の年齢へ転用せず、サイトの写真や訴求はそのジムの客層に合わせる。
実際の候補顧客には、現在の集客方法、直近の更新作業、困った場面、費用への疑問を聞き、本人の言葉とこちらの解釈を分けて記録する。
操作確認では、事前説明を最小限にして課題を渡し、迷った場所・完了できたか・かかった時間を記録する。想定と違った内容を優先してペルソナへ反映する。
