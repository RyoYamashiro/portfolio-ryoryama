# ジム特化の事業・開発方針

作成日：2026-10-29。固定の期限や日数ノルマは設けず、完成条件を一つずつ満たして進める。

## 現在の目的

パーソナルジム向けテンプレートを1つ、顧客に見せてテスト販売できる状態にする。
既存のSTELLA GYMを仕上げ、CMSでの更新、デモ公開、導入手順までつなぐ。他業種のテンプレートは現在の開発対象にしない。

事業の価格・ターゲット・販売条件は [共通の事業方針](business-policy.md) を参照する。この資料は現在の作業範囲と進め方を管理し、価格などを重複管理しない。
以下の実装順は作業案。未確定の提供条件や機能を、販売上の約束として扱わない。

## ジムサイトで伝えること

商品開発は [3人の顧客ペルソナ](gym-personas.md) を軸に進める。経営者としての購入・更新の負担と、来店客の閲覧・予約体験を分けて判断する。

サイトを選ぶジム経営者と、体験を検討する来店客の両方を意識する。
来店客が「自分に合うか」「費用はいくらか」「誰が教えるか」「どこにあるか」「どう体験を申し込むか」を判断できる構成にする。

- 特徴・サービス：対象者、指導内容、他店との違いを具体的に伝える。
- 料金：プラン、含まれる内容、追加費用などを分かりやすく示す。
- トレーナー：写真、紹介、実際に確認できる経歴や資格を掲載する。
- 店舗情報：所在地、営業時間、アクセス、問い合わせ先を確認できるようにする。
- FAQ：体験、持ち物、初心者の不安など、実際の質問に答える。
- お知らせ・ブログ：公開記事を一覧・詳細から読めるようにする。
- 体験予約：設定した予約先へ迷わず進めるようにする。

強い色や筋肉の写真だけでジムらしさを表現しない。想定する客層・価格帯・指導方針から印象を決め、[デザイナーの基準](roles/designer.md) に沿って視認性と信頼感を保つ。
実績、口コミ、資格、身体の変化などを創作しない。デモの仮情報と実店舗の情報を区別する。

## 来店客のインサイトとデザイン

健康への安心感、Before / Afterに感じる「自分も変われるかもしれない」という希望、より魅力的な自分になりたいという少しの野望を、デザインの軸にする。
これは来店動機の仮説であり、全員に同じ願望を当てはめない。顧客の言葉や店舗の客層を見ながら調整する。

| 気持ち | デザインへの反映 |
| --- | --- |
| 健康的に過ごしたい、安心して任せたい | 清潔感のある色と写真、読みやすい文字、落ち着いた余白、親身なトレーナーの表情や指導場面で伝える |
| 今の自分から変わりたい、新しい自分に期待したい | 明るい自然光、前向きな姿勢、生活の変化を想像できる写真と文章で、無理なく一歩踏み出せる希望を伝える |
| 格好よく・美しくなりたい、自信を持ちたい | 服を楽しむ姿や自然な笑顔、さりげない洗練で表す。露骨な性的訴求や他人との優劣に頼らない |

中心となる感情の流れは「ここなら安心できそう → 自分にも変化がありそう → 少し始めてみたい」。固定のページ順ではなく、写真・コピー・配色・余白・予約導線がこの気持ちを支えるかで判断する。

- 「イケメン・美女になりたい」という願望は内部の理解に活かし、表のコピーでは「好きな服を楽しむ」「自分に少し自信が持てる」など自然な日常の言葉へ翻訳する。
- 今の体型や年齢を否定したり、恥・不安・劣等感を煽ったりしない。変わることを押しつけず、本人の望む変化を応援する。
- 安心感を土台に、希望や高揚感をアクセントで足す。強い色や大きな煽り文句、過剰な筋肉・美貌の写真で画面全体を埋めない。
- Before / Afterは必須の構成ではない。掲載する場合は本人の許諾と実際の記録に基づき、期間・条件・個人差を明示する。加工やAI生成で成果を捏造せず、同じ結果や健康改善を保証しない。
- 読みやすさ、料金の明確さ、指導内容の具体性を保ち、雰囲気だけで安心を演出しない。

## 現在の出発点

作成時点では、ジムのデザイン、セクション別コンポーネント、ローカルの内容データ、テーマカラーの簡易プレビューがある。
外部CMSは未接続。既存の学習用管理画面で記事を編集してもジムの表示には反映されない。ブログ・予約はデモ動作で、テーマ色は保存されない。
詳細な現状と編集箇所は [README](../README.md) と [ジム編集ガイド](gym-template.md) を参照し、着手時にはコードと照合する。

## 完成条件

- [ ] ジム1店舗分のサービス・料金・トレーナー・FAQ・店舗情報が、スマートフォンとPCで読みやすく表示される。
- [ ] 採用CMSと顧客が更新できる項目が決まり、対象項目の変更がサイトに反映される。
- [ ] お知らせ・ブログの公開記事を読め、下書きが公開されない。
- [ ] 体験予約の導線が設定した外部予約先等につながる。未設定時に予約可能と誤認させない。
- [ ] デモサイトを公開し、仮情報・デモ機能を明示する。
- [ ] SEO共通チェックリストの適用項目を確認し、公開環境のインデックス方針を設定する。
- [ ] 顧客が準備する情報、導入手順、更新方法、継続費用、サポート範囲を説明できる。
- [ ] 別のジムの情報へ差し替える導入リハーサルを行い、所要時間とつまずきを記録する。

## 進める順番の目安

| 段階 | 作業 | 到達点 |
| --- | --- | --- |
| 1. 範囲を決める | 商品範囲、CMS、更新項目、予約先、公開先を決める | 実装対象と顧客・開発者の担当範囲が分かる |
| 2. 更新をつなぐ | CMS接続、ジム情報の表示、お知らせ・ブログを実装 | CMS更新から公開画面への反映を確認できる |
| 3. 使いやすく整える | 予約導線、デザイン調整、スマホ対応、SEOを整える | 顧客に見せる主要導線が一通り動く |
| 4. 公開・導入を整える | デモ公開、実環境の確認、導入・更新手順の作成 | デモを共有し、導入方法を説明できる |
| 5. 販売に備える | 別店舗への差し替え確認、不具合修正、営業用の説明整理 | テスト販売に持ち込める |

SEOは後回しにせず、各実装時に [エンジニアの基準](roles/engineer.md) と [SEO共通チェックリスト](../SEO_COMMON_CHECKLIST.md) を参照する。
販売LPの作り込みや発信量の拡大より、まずデモと料金・提供範囲・導入の説明をそろえる。

## 着手時に決める項目

- CMSと公開先：現在の費用・制約を確認して選ぶ。選定のための比較を長引かせない。
- CMS更新範囲：店舗情報、料金、トレーナー、FAQ、お知らせ・ブログを候補に、必要な項目へ絞る。
- テーマカラー：CMS保存を今回の必須にするか、開発者による初期設定にするかを決める。現状のパレットを保存機能として販売しない。
- TypeScript：事業上の想定技術として、移行範囲と工数を決める。未移行を実装済みと説明しない。
- 導入・運用：アカウント所有者、初期設定の担当、費用、修正・サポートの範囲を共通方針へ反映する。

## 今は広げないこと

- 美容サロン・飲食店など他業種の制作、複数デザインの量産。
- 独自の予約管理、決済、会員管理、顧客管理システム。
- 自由配置できるページビルダーや、多店舗・多業種を一括管理する基盤。
- 必要性が確認できていない検索、多言語、高度な承認フロー。
- 販売可能な状態に近づかない大規模な共通化や、見た目の全面作り直し。

新しいアイデアは保留事項として残し、今の商品に必要かを判断してから追加する。負担が大きい場合は、未販売の追加機能や装飾から範囲を縮め、安全な公開・更新・導入に必要な確認は省略しない。
