# 挫折しにくい順番で育てよ〜💅

日本一を目指す目標は持ったまま、今日の作業は小さくしよ！
**1回に変えるのは1つ、動いたら区切る**。わからない部分が残っていても、次の一歩を選べれば進んでるよ。
日数のノルマはなし。下の「できた目印」が出たら次へGO！

## Step 1：起動して、保存する

[README](../README.md)の手順で `npm run dev` を起動し、記事のタイトルを変更してみてね。
できた目印：JSXやJSONファイルを直接編集せずに、閲覧画面の記事が変わる。今日はこれで終了でもOK！

## Step 2：画面を1行だけ変える

`app/page.jsx` の見出し「記事一覧」を「私のブログ」に変えてみよ。
保存すると開発サーバーが変更を反映するよ。変わらなければブラウザを再読み込みしてね。
できた目印：画面の見出しが変わる。記事データとは別の場所を編集しているって説明できる！

## Step 3：APIを見る

`/api/posts` をブラウザで開こう。管理画面で下書きを作って、JSONに混ざっていないことを確認。
次に公開へ変更して、APIを再読み込みしよ！
できた目印：「画面が記事を持ってるんじゃなく、APIから受け取る」と説明できる。

## Step 4：小さく1機能足す

まずは `app/posts-view.jsx` の一覧に「公開記事が何件あるか」を表示してみよ！ `posts?.length` がヒントだよ。取得前の `posts` は `null` だから、読み込み中は件数を出さず、取得後に表示しよう。
できた目印：記事を公開・非公開にすると、再読み込み後の件数も変わる。

次の練習候補は「概要」。やるなら別の日に、こんな順番で1項目だけ増やすと追いやすいよ。

1. 概要の名前・必須かどうか・文字数を決める（例：`summary`、任意、200文字）。
2. `cms/posts.js` で検証し、`cms/api.js` で保存する項目に加える。
3. `app/admin/editor.jsx` に入力欄と送信処理を足す。
4. `app/posts-view.jsx` に表示処理を足す。過去の記事に概要がない場合も扱う。
5. 作成・編集・再起動で概要が残ることを確認する。

できた目印：フォーム → API → 保存 → 表示まで、追加した項目を追える！

## Step 5：既存CMSに置き換える

ここまで慣れたら、外部CMSを1つだけ選ぼう。microCMSでも、WordPressのREST APIでもOK。
ReactとNext.jsは導入済み。次はデプロイと同時に進めず、まず外部CMSへの接続だけ！

1. CMS側に `title` と `body` に相当する項目を作り、公開記事を1つ用意。
2. サーバー側からAPIを呼び、結果を確認する。秘密のキーはサーバーの環境変数に置く。
3. 外部CMSのデータを、今の画面が期待する記事の形へ変換する。
4. `/api/posts` の取得元を置き換える。公開状態の判定はCMSの仕様に合わせる。
5. 下書きが公開されないことと、通信失敗時の表示を確かめる。

外部CMSへ切り替えたら、記事の編集はそのCMSの管理画面で行うよ。
教材の `/admin/` とローカルJSONへの書き込みAPIは使わなくなるから、販売版から外す。二重管理にしないのがコツ！
できた目印：外部CMSで変更した記事が、今の閲覧画面に出る。

## Step 6：販売候補を1つ完成させる

「小さなお店のお知らせ」みたいな用途を1つ選ぼ。
Next.jsの土台に、デザインと公開方法を順番に足していこう。
この教材は販売用の完成テンプレではなく、そこへ進む練習台だよ！

できた目印：別の人が説明書だけで導入して、記事を更新できる。
導入してもらって詰まったところを直すのが、次の商品改善になるよ〜。

## 機能はこの順で検討するとラク！

| 時期 | 機能候補 | 学べること・目的 |
| --- | --- | --- |
| 今の次 | 件数、概要、カテゴリを1つずつ | データと画面の関係 |
| 外部CMS接続後 | 画像と代替テキスト | メディアとアクセシビリティ |
| 記事が増えたら | ページ分割、検索 | 一度に取るデータ量の調整 |
| 公開を始める前 | 認証・権限、秘密の管理、バックアップ | 安全に編集・復旧できる運用 |
| 販売版の土台 | メタ情報、OGP、サイトマップ、適切なHTML生成 | 検索・共有で記事情報を届ける |
| 更新が増えたら | Webhookとキャッシュ更新 | 記事更新を表示へ反映する仕組み |
| チーム利用になったら | 認可つき下書きプレビュー、承認、履歴 | 誤公開の防止と編集作業の支援 |
| 必要な購入者がいたら | 多言語、会員向け記事 | 権限・翻訳・運用設計 |

Webhookは「記事が変わったよ」という通知、キャッシュは「取得結果の一時保存」だよ。今は名前だけ知っておけばOK！
未来の機能を全部入れる必要はないの。購入者が必要とするものだけ足していこ。

## 壊れにくくする、小さな習慣

- 動いた状態をGitのコミットやフォルダのコピーで残してから変更する。
- APIや保存処理を変えたら `npm test`。画面はブラウザでも確認する。
- 記事の項目名を変えるときは、すでに保存した記事をどう移すかも考える。
- 画面で使うデータの形をそろえ、CMS固有の処理は取得側へまとめる。
- 教材のデータはサーバー停止後に `data/posts.json` をコピーしてバックアップする。

「未来に絶対壊れない」は約束できないけど、変更する場所を狭くして、戻れる状態を作ることはできるよ。
今日は記事を1つ更新できたら十分。次はその処理を自分の言葉で説明してみよ〜！
