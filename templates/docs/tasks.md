## 今後の実装予定：簡単モード／通常モード

状態：未着手。まず通常モードで更新できる状態を作り、その後に簡単モードを追加する。初期販売の必須条件にはしない。

### 目指す体験

| モード | 主な用途 |
| --- | --- |
| 簡単モード | サイトの見た目から「✏️ 編集」を押し、文章・料金・写真などを変更する |
| 通常モード | 既存CMSの管理画面で、記事の作成、公開設定、項目の追加などを行う |

編集モードへ入る入口と、簡単モード・通常モードを使い分ける導線を用意する。
通常モードが外部CMSの別画面になる場合は、「サイト上で編集」「管理画面を開く」など実際の動作が伝わる名称を候補にする。ボタン名と画面構成は実装時に決める。

### 共通の前提

- 両モードの保存先は同じCMSに統一する。データを二重管理せず、変更内容と下書き・公開状態を両方で整合させる。
- 一般公開画面には編集操作を出さない。編集権限はサーバー側で検証し、アイコンを隠すだけで保護しない。
- 書き込みAPIの利用条件、認証・認可、入力検証、秘密情報の管理を確認する。セキュリティの検証は省略しない。
- 保存と公開を区別し、「保存しました」が下書き保存か公開反映かを明確にする。
- CMSとの通信処理と表示部品を分け、段階的に編集機能を追加する。将来のためだけの大規模な抽象化は行わない。

### 段階的なタスク

- [ ] 通常モードを実際の対象者に使ってもらい、編集場所・保存・公開で迷う点を確認する。
- [ ] ジム名・紹介文・料金など少数の項目で、簡単モードの操作試作を作る。
- [ ] 編集モードの入口、編集箇所の表示、保存・キャンセルの操作を検証する。
- [ ] 未保存の変更、画面移動、保存失敗、同時編集による上書きへの対応を設計する。
- [ ] 同じCMSへの安全な書き込みと、両モードでの反映・公開状態の整合を検証する。
- [ ] 操作確認で必要と分かった項目へ広げ、短いマニュアルを用意する。

### 操作仕様の検討メモ（未確定）

ユーザー案は、各項目の鉛筆アイコンから編集し、同じ位置に更新ボタンを置くこと。別項目・別画面へ移る際の「更新しますか？」確認も候補にある。
代案として、項目間の移動では入力内容を保持し、未保存表示と一括保存を用意して、ページを離れるときに確認する方式がある。
どちらも確定仕様ではない。モーダルの頻度、項目単位と一括保存の違い、スマートフォン操作を試して決める。ブラウザを閉じる際の確認にはブラウザ側の制約があるため、実装時に区別して扱う。
